# Digital Twin AI

- Работай как ведущий оркестровщик: цель → изучение проекта → необходимые
  вопросы → требования/приёмка → план → исполнение → независимая проверка →
  исправления → передача и сохранение состояния. Порядок и условия перехода —
  `docs/AGENT_WORKFLOW.md`; применяй их к каждой новой задаче этого проекта.
- Критерий завершения относится к цели пользователя. Для настройки оркестрации
  проверяй инструкции, выбор исполнителей, evidence и продолжение после restart;
  требования полной сдачи модели применяй только к задаче соответствующей сдачи.
- Codex ведёт процесс в текущем чате. Подзадачи поручай доступным исполнителям
  по контракту из AGENT_WORKFLOW; штатные агенты и готовые инструменты предпочтительны.
  Внешний Cursor CLI — подключённый дополнительный проверяющий, не обязательная
  точка входа. Пользователь ставит цель обычным языком без ручного запуска скриптов.
- Начинай с короткого `STATE.md`, затем выбери маршрут в `docs/TASK_CONTEXT.md`.
  При первом знакомстве с проектом прочитай бриф и три профиля целиком;
  при продолжении читай нужные разделы/страницы, не всю историю заново.
- Соблюдай `docs/AGENT_WORKFLOW.md`: узкая задача, файловые артефакты,
  компактные отчёты, проверки по затронутым рискам. Историю не загружать без причины.
- Область этих правил — весь репозиторий. Общайся по-русски.
- При моделировании соблюдай `docs/GEOMETRY_RULES.md`: квады, логические группы
  (body/окна/крыша), допустимое врезание ≥10мм; после финального Attach — без дублей и overlaps.
- BODY: только наружные фейсы, без интерьера. Резы по углам и реальным проёмам;
  сначала чистая наружная сетка с отверстиями, затем Shell внутрь0.4м, затем окна.
- Импорт и успешное открытие файла не означают готовую модель: обязательна проверка топологии.
- UV НПМ/ВПМ: соблюдай `docs/UV_RULES.md` — повторное использование областей по отделке,
  намеренные UV-overlaps, цель один UDIM на текстурный ID; без растяжения и раздувания тайлов.
- Для НПМ-ОКС не применять плотность Ground (PDF10, раздел6). Размер рисунка материалов
  должен совпадать с принятой ВПМ; проверять сохранённые UV и сравнение с одинаковой камерой.
- Оригиналы: `standards/source/` и три YAML в `standards/`. Не меняй нормы молча.
- Источник спорного правила — страница PDF; фиксируй расхождения в `docs/decisions/`.
- Бриф и технические решения не являются дополнительным ТЗ заказчика.
- Синтетические данные всегда помечай; не выдавай их за сведения реального ОКС.
- Не перезаписывай approved-решения. Новое предложение сохраняй отдельно как конфликт.
- Если пользователь называет результат успехом («круто получилось», «справился»,
  «принято» и аналогично), до конца текущего этапа зафиксируй опыт по
  `docs/EXPERIENCE_CAPTURE.md` и `docs/case_studies/TEMPLATE.md`.
  Обнови реестр `docs/case_studies/README.md` и `STATE.md`; сохраняй точную область
  приёмки, доказательства, неудачи и кандидатов на переиспользование.
  Перед сходной задачей прочитай релевантный опыт из реестра. Похвала не заменяет QA;
  универсальный Skill/автосборку не объявлять до проверки на втором проекте.
- Проверяй фактические файлы после упаковки и повторного импорта, а не только сцену.
- `passed=true` запрещён при невыполненных обязательных проверках или ручных воротах.
- Используй Context7 для документации библиотек; при недоступности отмечай ограничение.
- Проверки: `python -m pytest -q`, `dt profiles check`, `dt schemas --check`.
- DCC-тест: `dt build --job jobs/SYNTH-001/project.json --blender <blender.exe>`.
- После этапа обнови `STATE.md`: коммит, команды, результаты, ограничения, следующий шаг.
- Для навигации по направлениям и текущим PR/Issues используй
  `docs/organization/PROJECT_MAP.md`; черновой PR не считай слитым в `main`.
- Для GitHub-задач соблюдай `docs/organization/GITHUB_CODEX_WORKFLOW.md`:
  сначала fetch и exact SHA `origin/main`, затем отдельный worktree/ветка.
  Dirty основной checkout не переключай и не очищай. Перед переносом локальных
  файлов запускай read-only `tools/project_hygiene.py`; публикуй только
  воспроизводимый код, техдокументацию, принятые решения и scoped опыт.
  Коммиты и draft PR разрешены в рамках задачи; merge — после review и явного
  решения пользователя. После merge перепроверь GitHub/main и обнови STATE.
