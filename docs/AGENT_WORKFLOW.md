# Порядок работы оркестровщика Codex

Этот процесс обязателен через корневой AGENTS.md. Ведущий принимает обычную
постановку пользователя, выбирает маршрут и отвечает за соответствие результата
именно этой задаче. Детальные процедуры и нормы берутся из существующих профилей,
skills и инструментов. Не создавай новую платформу или документы-дубли.

## Цикл задачи и условия перехода

1. **Цель и изучение.** Прочитай короткий STATE, выбранный TASK_CONTEXT, нужный
   кейс и реальные входы/инструменты. Зафиксируй цель, границы и сохранённые
   решения пользователя. Найденный скрипт/MCP не считать работоспособным без evidence.
2. **Необходимые вопросы.** После изучения спроси только то, что меняет результат,
   входы, архитектуру или критерии. Обычные технические решения принимай сам;
   полезную независимую работу продолжай, пока ожидаешь существенное решение.
3. **Требования и приёмка.** В существующем job/spec/документе запиши входы,
   ограничения, ожидаемые артефакты, конкретные критерии и непроверенные ворота.
   Для небольшой правки достаточно короткой записи; новые job-файлы нужны для
   многоэтапной работы. Не подменяй задачу пользователя демонстрацией инструмента.
4. **План.** Определи этапы/зависимости, переиспользуемые инструменты, проверки,
   владельцев файлов/сцен/портов/output и безопасное повторение. Существенное
   неразрешённое решение блокирует только зависимые этапы.
5. **Исполнение.** Выполняй разрешённый план узкими этапами, сохраняя версии,
   фактические артефакты, manifests и evidence. Один владелец изменяет одну DCC
   сцену; параллельно допустимы независимые файлы, исследования и копии данных.
6. **Независимая проверка и исправления.** Передай требования и реальные
   артефакты проверяющему. Его завершение, exit0 и отчёт исполнителя не заменяют
   проверки. Классифицируй ошибку: source/tool/code/test/contract; исправь причину,
   повтори затронутые проверки. Обязательный failed-критерий не переводится в pass
   изменением формулировки. После двух повторов одной причины останови этот путь,
   сохрани состояние и предложи следующий обоснованный шаг.
7. **Передача и продолжение.** Сверь результат с исходной целью, сообщи что
   реализовано/проверено и что осталось. Обнови STATE: текущий этап, версии,
   evidence/команды, решения, блокеры и точный следующий шаг. При restart сначала
   проверь сохранённые результаты/хеши; не повторяй уже завершённую мутацию.

Неприменимый этап можно пропустить с причиной. Для конфигурации оркестрации
приёмка — действующие инструкции, работающий маршрут исполнения/проверки и
проверенное сохранение/возобновление; статус сдачи пилотной модели — отдельный
результат. Проверки модели становятся обязательными в соответствующей задаче.

## Делегирование

Ведущий остаётся в текущем чате; пользователь не должен вручную координировать
исполнителей. Простую задачу может выполнить один агент; отдельный проверяющий
полезен для кода, DCC и значимых изменений. Используй штатных доступных subagents
с наследованием модели; настроенный Cursor CLI можно привлекать в его разрешённой
области. Его запуск и native dt-verifier проверены: docs/organization/local-orchestration/CURSOR_CLI.md.

Каждое поручение содержит: цель; релевантные ссылки; входы/зависимости; разрешённые
файлы и ресурсы; запрещённые изменения; ожидаемый артефакт; критерии/команду QA;
формат возврата. Возврат: changed files/artifacts; реально выполненные проверки;
evidence paths; ошибки/блокеры; следующий шаг. Только ведущий принимает этап.
Для независимого кода используй worktree или непересекающееся владение; worktree
не изолирует DCC, MCP port и общий export. Передача таких ресурсов последовательна.

## Контекст и исполнение

1. Читать `STATE.md` и один маршрут `TASK_CONTEXT.md`; расширять контекст только
   при обнаруженной зависимости или противоречии.
2. До изменения определить вход, ожидаемый выход, файлы и критерий готовности.
   Одновременно решать одну операцию.
3. Чистые вычисления держать в ядре, DCC-вызовы — в адаптере, параметры объекта —
   в job/config, ручные решения — в реестре с источником.
4. Полные массивы, сцены и логи хранить в файлах. В отчёте давать числа,
   статусы, до пяти ошибок и пути к полному evidence.
5. `AdapterReport` описывает операцию, а не готовность всего ОКС.
6. Для одного приложения выбирать один транспорт. Перед DCC-вызовом подтвердить
   процесс, документ/сцену, единицы, версию и новый output.
7. Повторный запуск пишет в новый output; approved-файлы не перезаписываются.
   Кэш допустим только при совпадении входов, параметров и версии кода.
8. Проверять сначала затронутый риск, затем обязательные проверки проекта.
   Текстовая правка не требует полного DCC-прогона; экспорт или геометрия требуют.
9. После упаковки или экспорта читать фактический файл обратно. Успешный import
   не заменяет topology/UV/material/visual QA.
10. Обновлять `STATE.md` коротко: база Git, результат, команды, ограничения и
    следующий шаг. Историю переносить в `docs/history/`, опыт — в case study.

Для GitHub различайте local QA, hosted Actions, пользовательскую приёмку и
публикацию. Draft не считать кодом `main`; PR #18 не трогать до нового указания.

Для многоэтапного профиля: docs/organization/local-orchestration/README.md.
SPEC/PLAN и run ledger держи у job; каждый attempt пишет в новую папку.
После produced при restart сначала перечитай evidence/hashes, не повторяй мутацию.
Два повторения одной причины останавливают путь; сохраняй failure и next action.
