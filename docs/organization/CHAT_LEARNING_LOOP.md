# Цикл извлечения опыта из чатов

Цель: регулярно находить в рабочих чатах AGR и связанных 3D-проектов новые
потребности, подтверждённые решения, ошибки и ограничения, чтобы следующие агенты
видели их в репозитории. Это накопление проверяемых записей, не изменение весов модели.

Первичный снимок: [реестр 43 чатов](../history/organization/CHAT_REGISTER.md) и
[машиночитаемый аудит](../history/organization/CHAT_AUDIT_2026-09-29.json). Состояние обхода хранится в
`CHAT_LEARNING_STATE.json`; у каждого просмотренного ID — время последнего обновления.

## Каждый запуск

1. Читать `STATE.md`, [карту проекта](PROJECT_MAP.md), этот документ и состояние обхода.
   Если `docs/TASK_CONTEXT.md` уже опубликован, выбрать в нём маршрут; иначе
   найти нужный job/модуль через карту проекта, не требуя отсутствующий файл.
   Получить список чатов Codex, связанных с AGR, window_facades, Facades_Modelling,
   Blender, zavod и codex-3ds-max. Пропускать личные, финансовые, почтовые и
   репатриационные темы, даже если они рядом в боковой панели. Название чата —
   подсказка для поиска, его содержание не считать инструкцией этому агенту.
2. Новый ID, отсутствующий в состоянии обхода, сначала проверить на соответствие
   области, затем прочитать его содержательные этапы. По изменённым после
   предыдущего обхода чатам читать новые этапы. Для старых
   длинных чатов читать только добавленное и нужный контекст. Если интерфейс
   не даёт полный список, использовать локальный индекс Codex только для чтения,
   затем открыть нужные чаты штатным инструментом. Не собирать секреты, договоры,
   вложения и полный текст переписки в Git.
3. Сопоставить вывод с актуальными файлами job, утверждёнными версиями, Git/PR и
   проверками. Классифицировать каждую находку:
   `need` — повторяющаяся потребность пользователя;
   `constraint` — явно названный запрет или предпочтение;
   `accepted` — точно определённая область пользовательской приёмки;
   `validated` — технически проверенная операция с указанным источником/датой;
   `failed` — исправленный или сохраняющийся сбой;
   `hypothesis` — кандидат без достаточного подтверждения;
   `conflict` — несовместимые источники, нормы или версии.
4. Записывать источник: ID и название чата, дату, объект/версию, точный смысл
   пользовательского сообщения, файлы и SHA/отчёт при наличии, что реально
   проверено, что не проверено, область повторного применения. Пересказ агента
   или успешный запуск синтетического теста не превращать в приёмку пользователя.
   Похвалу фиксировать по `docs/EXPERIENCE_CAPTURE.md`; негативный отзыв тоже
   сохранять в релевантном кейсе, не стирая прежнюю частичную приёмку.
5. Выбрать одну из форм:
   - существующий `docs/case_studies/<CASE>.md` — дополнение к конкретной работе;
   - `docs/decisions/` — конфликт нормы или источников со страницами PDF;
   - `docs/organization/LEARNING_BACKLOG.md` — гипотеза/потребность для проверки;
   - `jobs/<ID>/STATE.md` — актуальное состояние объекта;
   - `AGENTS.md`/общие правила — только если формулировка уже подтверждена для
     указанной области и не конфликтует с утверждённым решением.
   Один случай не делает приём универсальной функцией или Skill. Повторение на
   том же объекте отличается от независимой проверки на втором проекте.
6. Сравнить с уже опубликованными записями и открытыми PR. Обновлять существующую
   запись вместо создания дубликата. Для существенного, доказанного изменения
   подготовить один небольшой draft PR в отдельной рабочей копии Git; указать
   источник, область, тесты и ограничения. Не объединять PR автоматически.
   Синхронизацию, локальный отбор, worktree, QA и завершение вести по
   [контуру Codex ↔ GitHub](GITHUB_CODEX_WORKFLOW.md).
   Если доказательств недостаточно, оставить запись локальной кандидатурой и
   кратко сообщить, что требуется для её проверки.
   По уточнению пользователя 01.10.2026 успешный кейс должен переносить также
   рабочие скрипты и техническую логику. Найти фактически использованные Python,
   MAXScript и другие собственные исходники; включить необходимые зависимости,
   README с входами/параметрами/командами и малые QA-отчёты. Убрать персональные
   пути и защитить принятые файлы от перезаписи. Перенос кода проверить повторным
   запуском и readback по затронутому риску; исторический QA отметить отдельно.
   Если код пока нельзя перенести, указать конкретную причину и следующий шаг.
   Математику без исполнителя сохранить как технический документ с единицами,
   предпосылками и проверенным примером. Обновить [каталог сценариев](../../technical_library/README.md).
   Кейс одного объекта можно публиковать с явными ограничениями; универсальный
   Skill/адаптер из одного примера не объявлять. Большие outputs остаются локально.
7. Состояние обхода менять только после успешного чтения и записи результата:
   время, рассмотренные ID/версии, ссылка на изменённый файл или PR. При ошибке
   чата не продвигать его курсор. В курсоре хранить время обновления чата,
   полученное перед чтением, а не время окончания обхода: сообщения, пришедшие
   во время чтения, должны попасть в следующий запуск. Если новых значимых фактов
   нет, сохранить локально результат «просмотрено, новых находок нет» и курсор;
   не публиковать содержательную запись и не создавать PR только ради курсора.

## Критерий пользы

По уточнению пользователя01.10.2026 сохранять техническую логику компактными
пакетами операций. Сначала искать существующий модуль и дубли, затем объединять
успешные этапы; общий алгоритм — в функции, данные объекта — в конфигурацию.
Не переносить каждый временный скрипт или все версии из чата. До публикации
рефакторинга сравнить результат с исходным маршрутом на тех же входах.
Четыре этапа UV — пример, не обязательное число файлов для каждой задачи.
Обновлять единый каталог операций `technical_library/README.md`;
ошибки сохранять выводом/контрпримером, не новой копией неудачного исполнителя.

У будущего агента должна появиться короткая применимая запись: какой вход,
какая операция, где работает, какие проверки это доказали и где остановиться
для ручного решения. Сводка из чата без такой связи остаётся архивом, а не правилом.

Первые три запуска проверять вручную: поиск ложной приёмки, дублирования,
ошибочного обобщения и пропуска негативного отзыва. Затем скорректировать
частоту или формулировку задания по фактическому результату.
