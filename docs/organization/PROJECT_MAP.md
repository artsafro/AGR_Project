# Карта AGR_Project

Актуальность: 29.09.2026. Это указатель на файлы и PR, а не свидетельство готовности
реальных ОКС. Репозиторий один: `artsafro/AGR_Project`. Исходные рабочие папки и
игнорируемые результаты DCC сохраняются отдельно до проверки резервной копии.

## Где искать

- `standards/` и `docs/decisions/` — источник норм, страницы PDF и расхождения.
  Три YAML не меняются по пересказу чата.
- `src/dt_ai/` — независимое ядро; `adapters/` — выполнение в Blender, Max,
  Revit и CAD. Доступность адаптера проверяется в текущем сеансе.
- `jobs/<ID>/` — объект, входы, версии и его `STATE.md`. Файлы в `outputs/`
  обычно игнорируются Git и не восстанавливаются из клона.
- `max/AGR_Workbench/` — планируемый перенос собственных инструментов Max.
- `docs/case_studies/` — подтверждённый опыт с точной областью приёмки,
  неудачами и непроверенными пунктами.
- `docs/organization/` — карта чатов, процесс извлечения опыта и миграция.

Перед задачей читать корневой `STATE.md`, затем маршрут `docs/TASK_CONTEXT.md`,
если он уже опубликован, затем состояние конкретного job. Когда маршрута в ветке
ещё нет, искать нужный job/модуль по имени; не считать локальный checkout равным
`main`.

Очередь GitHub: [резервная копия #6](https://github.com/artsafro/AGR_Project/issues/6),
[CI #7](https://github.com/artsafro/AGR_Project/issues/7),

[кейсы объектов #12](https://github.com/artsafro/AGR_Project/issues/12),
[внешние инструменты #13](https://github.com/artsafro/AGR_Project/issues/13),
[конфликт норм #14](https://github.com/artsafro/AGR_Project/issues/14).

1. `AdapterReport`: контракт, схема, reader и тесты. Затем геометрические
   адаптеры Connect/Exterior/Shell вместе с обёртками и тестами.
2. AGR Workbench и инструменты атласов: собственный код, происхождение,
   воспроизводимая проверка и граница применимости. Чужие плагины не копировать
   без проверки лицензии.
3. `REVIT-OPENINGS`, Ground, MASHI, Object013, ГЛБ и знаки: отдельные записи
   по объектам. Приблизительные модели и отклонённые версии не помечать как
   принятые; визуальную и DCC-проверку не заменять тестом Python.
4. Инструменты из связанных рабочих папок переносить по одному с хешем,
   исходным путём и проверкой. Старые папки пока сохранять.

Для каждого результата вести четыре независимых статуса: реализация,
техническая проверка, пользовательская приёмка, публикация. Изменение документа
или публикация PR не переводят модель в `passed=true`.

## Открытые организационные ограничения

- Принятые файлы Обр22 перечислены в `jobs/OBR22-K02/APPROVED_VERSIONS.json`
  ветки PR #4; для них нужна проверенная резервная копия вне репозитория.
- CI ранее возвращал `startup_failure`. Отдельно проверить новый запуск и
  установку optional зависимостей `contour-model`; локальный тест не заменяет CI.
- Новая редакция PDF и старые утверждённые YAML требуют отдельного сравнения
  применимости со страницами, а не тихой замены норм.
- Защита `main` не подтверждена. До её настройки использовать небольшие PR и
  явно фиксировать проверки и ограничения.

Детальный порядок и инвентарь: локальный
`docs/organization/GITHUB_ORGANIZATION_PLAN.md`. Пока он не опубликован,
не ссылаться на него как на доступный файл `main`.
