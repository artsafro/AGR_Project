# Постоянный контур Codex ↔ GitHub

Цель — держать `main` компактным источником подтверждённого состояния проекта,
а локальные DCC-сцены, outputs и временные попытки использовать как рабочие входы.
Это накопление проверяемого опыта и кода, а не переобучение модели.

## Что хранится в GitHub

- исполняемые `src/`, `tools/`, адаптеры и их тесты;
- нормы, схемы, ADR и решения с источниками;
- компактные пакеты `technical_library/` с README и QA;
- case studies с точной областью пользовательской приёмки, ошибками и ограничениями;
- job-конфигурации, manifests и короткий `STATE.md`, если они не содержат секреты
  и не зависят от персонального абсолютного пути.

Не публикуются DCC-сцены и большие FBX/PNG, `outputs/`, кэши, временные логи,
полные чаты, секреты и многочисленные варианты одного скрипта. Hash-манифест
описывает локальный файл, но не является его резервной копией.

## Цикл каждой новой задачи

1. **Синхронизация.** Прочитать корневой `STATE.md` и маршрут
   `TASK_CONTEXT.md`. Выполнить `git fetch`; зафиксировать SHA `origin/main`,
   текущую ветку и dirty-состояние. Новую задачу начинать в отдельном worktree
   и ветке `codex/<scope>` от свежего `origin/main`. Dirty checkout не очищать.
2. **Инвентаризация.** Выполнить read-only аудит:

   ```powershell
   python tools/project_hygiene.py --root . --output tmp/project-hygiene.json
   ```

   Аудитор не следует по symlink/reparse, учитывает ошибки чтения и помечает
   чувствительные имена/маркеры без вывода их содержимого. Отдельно проверить
   фактические локальные входы нужной операции. Отчёт лишь предлагает категории;
   он не разрешает автоматически публиковать файл.
3. **Отбор.** Для каждого кандидата определить источник, назначение, актуальную
   версию, зависимости, проверку и статус принятия. Искать существующий модуль,
   кейс и открытый PR; обновлять их вместо копии. Персональные пути заменять
   параметрами. Неподтверждённое сохранять как backlog/hypothesis.
4. **Исполнение.** Codex может самостоятельно создавать небольшие тематические
   коммиты и публиковать draft PR в рамках поставленной задачи. Один PR содержит
   одну проверяемую цель. Большую миграцию делить на последовательные PR.
5. **QA и review.** Проверить затронутый риск, затем обязательные проверки
   проекта. Сверить exact head/base, передать diff независимому проверяющему,
   исправить findings. Локальный QA, hosted Actions, пользовательская приёмка и
   delivery фиксируются отдельно. Merge выполняется после review и явного решения.
6. **Интеграция.** После merge проверить GitHub `merged=true`, merge SHA и
   обновлённый `origin/main`. Следующую задачу снова начинать от нового main;
   завершённый worktree архивировать.
7. **Накопление опыта.** Принятый результат записать по
   `EXPERIENCE_CAPTURE.md`; переиспользуемый исполнитель — в существующий пакет
   technical library; конфликт — в ADR; текущий статус — кратко в `STATE.md`.
   Подробную завершённую историю переносить в `docs/history/`.

## Очистка без потери данных

Codex не удаляет локальные исходники только потому, что они не вошли в Git.
Сначала формируется список: `publish`, `keep_local`, `superseded`, `duplicate`,
`sensitive`, `unknown`. Удалять можно только воспроизводимые временные данные или
явно подтверждённые дубли после проверки путей и сохранения нужной версии.
Tracked-мусор удаляется отдельным reviewable commit с доказательством замены.

## Возобновление после нового чата

Новый чат не должен полагаться на память предыдущего. Достаточный вход:
`AGENTS.md` → `STATE.md` → `TASK_CONTEXT.md` → нужный job/case → свежий
`origin/main`. Если эти источники расходятся, GitHub main определяет опубликованный
код, а локальные файлы считаются кандидатами до сравнения и QA.
